# Technical decisions

- client_packages uniqueness: one package per Stripe session when participant_index is NULL, and one per (stripe_session_id, participant_index) when set (1..4) — keeps webhook double-delivery protection (P0-2) while allowing one package per participant for multi-participant stages.
- Stage 100% Glisse Stripe payments go only through stripe-webhook/stage.ts: amount_total must equal 250 € × participants, then a single book_stage_for_participants call; any mismatch or failure creates no booking and alerts the admin — keeps payments atomic and amounts truthful.
- Stage 100% Glisse checkout uses a dedicated per-participant Stripe price (quantity = participants, strictly 1..4); other activities keep the 50 € deposit price × sessions — the checkout amount must match what the webhook expects.
- Stripe recovery (sync-stripe-reservations) never books Stage 100% Glisse as à la carte: a stage payment is 'done' when a stage client_package exists for its stripe_session_id, otherwise left to A0 manual handling — stage bookings live in client_packages/package_bookings, not reservations.
- Stage packs created by online payment (participant_index set) get one global confirmation from the webhook; per-day booking confirmations and the low-credit warning are skipped during stage planning — avoids 6 e-mails and a false 'last session' alert.
- reservations.client_activity (NOT NULL) records the activity the client bought, distinct from daily_groups.activity (group origin); a BEFORE INSERT trigger fills it from the group when omitted so frozen booking functions keep working — group/client activities are never auto-synced afterwards.
- activity_group_compatibility (PK group_activity, allowed_client_activity) is the declarative source of which client activities may join/create which group type; read by admins/service_role only, never publicly writable.
- À-la-carte kitesurf group selection goes through find_or_create_compatible_group (kitesurf group → compatible open Stage group that already has ≥1 confirmed Stage booking (empty Stage groups stay reserved for indivisible Stage purchases) → new kitesurf group via find_or_create_daily_group, never a Stage group); it takes the Stage advisory lock then the Kitesurf lock for the date — Stage paths only take the Stage lock, so no inverse order/deadlock. Other activities keep find_or_create_daily_group unchanged.
- Admin move/reschedule of an à-la-carte reservation picks its target group from reservations.client_activity: kitesurf goes through find_or_create_compatible_group (never an empty or new Stage group), other activities and packs keep find_or_create_daily_group on the group activity; the reschedule e-mail shows the client activity — keeps admin paths consistent with booking rules.
- CRM (crm_client_base/crm_client_detail) reports a visitor reservation's activity from reservations.client_activity; package data keeps client_packages.activity and package bookings keep the group activity — the CRM describes what the client practised, not the group's origin.
- Admin reservation list shows reservations.client_activity as the main activity label and mentions the group activity only as secondary info when it differs.
- Revenue/season stats and assistant reservation metrics classify visitor reservations by reservations.client_activity; group/occupation metrics (sessions, fill rate, journées, remplissage) keep daily_groups.activity; package metrics keep client_packages.activity.
- New-reservation admin notifications (notify_new_reservation) title the reservation by reservations.client_activity and mention the group activity only when it differs; package booking confirmations keep the group/package activity — notifications describe what the client booked.
- MCP list_my_reservations reports each reservation's activity from reservations.client_activity (group activity only as fallback), keeping the same 'activity' field and user_id/RLS scope — the client sees what they booked.
- Waitlist: a seat freed in a Stage 100% Glisse group that already has ≥1 confirmed Stage booking is offered first to the Kitesurf waitlist as a targeted offer (daily_waitlist.offered_group_id), falling back to the Stage waitlist only when no Kitesurf offer is made or pending; a pending targeted offer holds its seats in waitlist_free_seats — prevents double-offering the same seat and keeps empty Stage groups out of the Kitesurf path.
